# jam

Rust daemon + Ratatui TUI that lets users see multiplexer-hosted coding agents and jump to the pane that needs attention.

## 1. Project Rules

- Keep `jam notify` hook-safe: it must be fast, quiet by default, and must not return a failing exit code to the calling agent hook.
- Preserve the daemon as an in-memory bulletin board. Do not add persistence, transcripts, cost tracking, or agent control unless the scope explicitly changes.
- Keep multiplexer-specific logic behind `src/mux.rs` and `src/mux/{tmux,zellij}.rs`; the daemon, protocol, and TUI should stay multiplexer-agnostic.
- Treat `hooks/<agent>/` files as shipped assets. `build.rs` embeds regular non-dotfiles into `setup::assets`; update the hook payload and installer behavior together.
- `jam setup` must be non-destructive: merge or skip existing config, preserve unrelated user keys, and use `--dry`/`--ask` behavior when changing install flows.

## 2. Verification

Use the smallest check that proves the change, then run the broader suite before handoff when behavior changed:

- `cargo test` — primary regression suite for protocol, registry, setup merge, mux helpers, and TUI ordering.
- `cargo clippy --all-targets -- -D warnings` — run for Rust logic changes before handoff.
- `cargo fmt --check` — run before handoff; if it fails on unrelated pre-existing formatting, report that separately instead of mixing formatter-only churn into a feature diff.
- `cargo test -- --ignored` — only for live multiplexer checks when intentionally testing ignored tests such as zellij focus behavior.
- `jam setup <agent> --dry` — inspect generated hook/config payloads without writing user files.

For multi-step tasks, use a brief plan with checks:

```text
1. [Step] -> verify: [check]
2. [Step] -> verify: [check]
3. [Step] -> verify: [check]
```

Strong success criteria let agents loop independently. Weak criteria require clarification.

## 3. In-Code Documentation

For public Rust items, use rustdoc (`///` or `//!`). For shipped TypeScript hook extensions in `hooks/pi/*.ts`, use concise JSDoc/TSDoc only when exporting reusable behavior.

- Document wire and runtime invariants that are easy to break blind: newline-delimited JSON in `proto::Request`/`proto::Response`, hook-safe zero-fail behavior in `notify`, sparse event field retention in `daemon::registry::Registry`, and pane/session uniqueness differences between tmux and zellij.
- Internal comments should explain why a constraint exists: stale timeout behavior, socket auto-start/reclaim choices, non-destructive setup merges, and multiplexer focus edge cases.
- If types and names make the behavior obvious, keep comments to a one-liner or omit them.

## 4. Key Decisions

- `src/main.rs` is the only CLI dispatcher: no subcommand runs the TUI except the no-args path, which calls `jam::tui::run()`.
- `src/proto.rs` owns the normalized model and wire protocol: `Agent`, `EventKind`, `Mux`, `Event`, `Session`, `Request`, and `Response` serialize as the newline-delimited JSON crossing the Unix socket.
- `daemon::registry::Registry` is the daemon's only state. `EventKind::End` removes a session, later sparse events preserve earlier optional fields, and `snapshot()` returns a deterministic session-id sort before the TUI reorders for attention.
- `daemon::connect_or_spawn()` is the shared client entry point for the TUI and `jam notify`; it auto-starts `jam daemon` and uses `proto::socket_path()` (`JAM_SOCKET`, then `XDG_RUNTIME_DIR`, then `/tmp`).
- `tui::event_loop::App` owns selection, messages, and attention sorting. `WaitingInput`/`Error` rows come first, stale rows last, and selection follows the same `session_id` across daemon broadcasts.
- `mux::focus()` is the sole focus boundary. tmux pane ids are server-global; zellij pane ids require `mux_session` and normalization to `terminal_<id>`/`plugin_<id>` forms.
- `setup::assets` is generated by `build.rs` from `hooks/`; installers such as `setup::claude::install` must consume embedded payloads rather than reading source-tree hook files at runtime.
